Sideout Engineering Spec

CV Phase 1: Measurement-Grounded Analysis

On-device pose estimation runs during frame extraction, computes biomechanical measurements per rep, and grounds the coaching-service scoring in measured values instead of visual guesses. Every analysis banks dense keypoints and a 24-frame set as the future training corpus.

01

Goal and non-goals

In scope

  • Pose estimation in a hand-rolled worker at the frame-extraction seam
  • Rep detection and a per-rep measurements block sent with the frames
  • Grounded rubric scoring for all six skills, confidence-gated
  • 24 frames stored permanently plus dense keypoints, corpus-ready
  • Skeleton overlays on the filmstrip and the clip player
  • Training-consent choice at first upload

Deferred, explicitly

  • Real ball detection (Phase 1.5, fed by this corpus)
  • Court calibration and absolute metric units (Phase 1.5+)
  • Storage-first frame upload past the request cap (Phase 1.5)
  • Focus-player identification (Phase 3)
  • Live per-rep practice feedback (Phase 2)
  • Native app; any response-schema change
02

Locked decisions

#Decision
1Ball detection deferred. ball_track stays model-sourced with a provenance marker. Contact detection comes from wrist kinematics.
2Two-stage capture: pose on the 24 existing probes finds peaks, then dense pose at 24 to 30fps in windows of about ±1s around each peak via muted segment playback with requestVideoFrameCallback.
3Units are body-relative plus absolute seconds. Every metric ships as {value, unit, confidence}. No fake absolute distances, ever.
4All six skills get measurements, gated by confidence: any metric below threshold is omitted entirely, never sent as a weak number. Three rep-detector families: swing (serve, attack), jump (block), platform/posture (pass, dig, set).
5Dense keypoints stored as keypoints.json in the frames bucket. 24 frames captured and stored permanently as corpus; the best 12 go to the model within the 4MB request cap.
6Web application first. Floor: Safari 16.4+ / Chrome 110+ on modern phones, with automatic fallback to the existing pipeline everywhere else. Nobody is ever blocked.
7Response schema frozen. Measurements are input-only. Existing eval cases pass unmodified.
8Training consent is an explicit opt-in/opt-out choice at first upload. profiles.training_consent defaults to false, is changeable in settings, and corpus queries hard-filter on it.

Architecture

Capture / uploadcomponents/analyze-flow.tsx: record, upload clip, or photos. Consent gate fires on first upload.
↓
Extraction, stage 1lib/frames.ts: pose on 24 probe frames, motion score = normalized wrist speed, peaks located.fallback: existing luminance scan, unchanged
↓
Extraction, stage 2Muted playback of ±1.2s windows around each peak, dense landmarks via requestVideoFrameCallback, global budget about 8s.fallback: skip window, no measurements for it
↓
Measurementlib/pose/kinematics.ts + lib/pose/metrics.ts: reps, joint angles, tempo, jump, each as {value, unit, confidence}; below-threshold metrics omitted.
↓
Analysis requestPOST /api/analyze: 12 pose-selected frames + optional measurements block. System prompts stay byte-stable and cached; measurements ride in the user turn.
↓
PersistenceRoute stores result + measurements + 12-frame keypoints, predetermines keypoints_path and stored_frame_paths. Client post-uploads keypoints.json and frames 13 to 24, non-fatal, same pattern as the clip.
↓
Resultsanalysis/[id]: filmstrip skeleton overlay from the row; clip player lazy-loads keypoints.json by signed URL; ball marker shows its estimated provenance.

The pose engine loads lazily on the analyze flow only. Nothing else in the app pays its cost.

Measurements block, wire shape v1

{
  "version": 1,
  "capture": { "dense_fps": 27, "coverage": "windows", "engine": "pose-landmarker-lite" },
  "units": "body-relative: heights in standing-body-heights, widths in shoulder-widths,
            angles in degrees, time in seconds",
  "reps": [
    {
      "start_s": 3.2, "contact_s": 4.1, "end_s": 4.9, "detector": "swing",
      "metrics": {
        "contact_height":          { "value": 1.28, "unit": "body_heights",    "confidence": 0.91 },
        "elbow_angle_at_contact":  { "value": 158,  "unit": "deg",             "confidence": 0.86 },
        "approach_tempo":          { "value": [0.61, 0.55, 0.34, 0.30], "unit": "s_between_steps", "confidence": 0.78 },
        "jump_height":             { "value": 0.21, "unit": "body_heights",    "confidence": 0.83 }
      }
    }
  ],
  "session": { "rep_count": 4, "contact_height_stddev": 0.05 },
  "omitted_below_confidence": ["toss_drift"]
}
  • Metrics below threshold appear only in omitted_below_confidence, names only, never values.
  • Empty reps means the block is not sent at all.
  • Server validation failure logs and proceeds as a no-measurements request. It never 400s the analysis.

  • No new buckets or policies. keypoints.json and x*.jpg live under the existing frames bucket at ${user.id}/${analysisId}/, covered by the existing own-folder RLS. Verify during M0 that the insert policy admits the browser client (same auth context as the route).

Stage 2 fails or exceeds budgetKeep stage 1 peaks, send no (or partial) measurements. Frames still improve via pose peaks.
Zero reps detectedNo measurements block; frame plan as today.
Measurements fail server validationLog, proceed as a no-measurements request.
Keypoints or extra-frames upload failsNon-fatal, same as the clip upload today. Overlay handles absence.

Invariant: no Phase 1 code path may make an analysis fail that would have succeeded before Phase 1.

10

Decision Log entries to record

D-008: pose engine dependency

Admit the pose library (Google-published, Apache-2.0, pinned exact version) under the D-001 10.5 gate. Analyze flow only, lazy-loaded; WASM and model assets self-hosted under public/pose/. Same entry clarifies scope of the vendor-name rule: it governs UI, user-visible errors, and marketing surfaces; package.json, imports, and engineering docs may name dependencies. UI copy calls the capability "motion tracking".

D-009: training corpus and consent

24 frames plus keypoints stored permanently per analysis as a future training corpus. Explicit opt-in/opt-out at first upload, default false, settings toggle, corpus access hard-filtered on the flag. Youth-footage rationale recorded.

Testing and verification

  • node --test on kinematics and metrics with recorded landmark fixtures per skill (a made serve, a shank, an occluded dig), asserting values, confidences, and omission behavior.
  • Extended frame-select tests for store/send planning.
  • Eval harness: every existing case passes byte-identically (schema frozen). New measurement-bearing cases replayed through /api/eval; grounded versus ungrounded comparison on the same frames is the M7 quality signal.
  • AI_MOCK=true unchanged; the mock ignores measurements.
  • Device matrix: recent iPhone Safari, recent Android Chrome, one old device proving the fallback, desktop. Added extraction wall-clock p50 under ~12s on a mid-tier phone.
  • Full production build plus the repo quality-floor checks at every milestone.

13

Acceptance criteria

  1. A serve or attack clip on a modern phone produces a measurements block with at least contact, tempo, and jump metrics at confidence ≥ 0.7, and the returned analysis cites measured values in its metric notes.
  2. All six skills produce keypoints and skeleton overlays; low-confidence metrics are absent from the payload, not present with low values.
  3. An old browser or failed engine load reproduces today's exact behavior with no user-visible error.
  4. A fresh analysis has 24 frames and keypoints.json in storage, with stored_frame_paths and keypoints_path set; the corpus query returns only consented rows.
  5. Every pre-existing eval case passes unmodified; the grounded eval run scores at or above the ungrounded baseline.
  6. No new colors, fonts, or vendor names in UI; the request body stays under the cap; hand-rolled worker and service worker only.
